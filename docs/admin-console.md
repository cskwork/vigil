# 프로젝트별 검증 관리

Vigil 관리 콘솔은 기획·QA 담당자가 프로젝트와 사이트를 등록하고, 사용자 시나리오를 요청하고 E2E 스크립트와 실행 결과를 관리하는 로컬 웹 앱입니다.

```sh
go build -o vigil ./cmd/vigil
./vigil -c vigil.yaml admin --addr 127.0.0.1:8787
```

## 처음 사용하기

1. **프로젝트·사이트**에서 프로젝트 이름과 URL을 등록합니다. ID, URL 호스트 허용, 읽기 전용 기본값은 자동으로 채웁니다.
2. 한 프로젝트에서 여러 사이트를 관리할 수 있습니다. 사이트마다 URL과 이름을 입력하고 기본 사이트를 선택합니다.
3. **검사 관리 → 검사 만들기**에서 검증 사이트를 선택하고 버그 재현 시나리오, 구현한 기능, 커밋 메시지·변경 내용을 자유롭게 적습니다. 기대 동작이 있으면 함께 입력합니다.
4. **시나리오 생성·검증**을 누르면 오케스트레이터가 브라우저 에이전트에 탐색과 스크립트 작성을 맡기고, 생성된 E2E 스크립트를 독립 실행해 확인합니다. 위치 선택이나 대기 등 스크립트 문제는 설정된 횟수 안에서 보완합니다. 기대 동작을 통과하도록 임의로 바꾸지 않습니다.
5. 실행 직후 진행 패널이 열립니다. 에이전트 연결, 사이트 탐색, 스크립트 검증과 실제 실행 단계를 보여 줍니다. 탐색 중 마지막 캡처가 갱신되고, 완료 시 결과 캡처를 바로 확인하거나 확대할 수 있습니다. 여러 스크립트의 결과를 각각 표시하며 일부 실행만 통과해도 전체 통과로 표시하지 않습니다.

대상 서비스 코드는 수정하지 않습니다. 버그 제보의 기대 동작과 실제 실행을 비교하며, 실패만으로 재현을 확정하지 않습니다. 필요한 로그인·명세·환경이 없으면 미확인 상태로 남깁니다. 커밋 해시만으로 내용을 안다고 가정하지 않으므로 메시지나 변경 내용도 함께 붙여 넣으세요. 작성된 YAML 스크립트는 **고급 · YAML 스크립트 가져오기**에서 직접 등록할 수도 있습니다.

자동 생성에는 기존 Pi 에이전트 설정과 인증, `agent_browser` 확장이 필요합니다. `agent.model` 또는 `agent.models`, `agent.thinking`, `agent.extension`을 설정하며 `vigil doctor`로 연결을 점검할 수 있습니다. 모델을 사용할 수 없으면 명시적으로 실패를 표시하고 요청을 종료합니다. 자동 재시도를 기다리는 대기열로 방치하지 않습니다.

## 화면 이미지와 녹화 영상으로 요청하기

글로 설명하기 어려운 상황은 화면을 그대로 올릴 수 있습니다. **새 검증 요청**에서 이미지(PNG, JPEG, GIF, WebP)나 녹화 영상(MP4, MOV, WebM)을 최대 8개, 합계 128MB까지 첨부합니다. 설명을 비워 두고 첨부만 올려도 접수됩니다.

에이전트는 첨부에서 화면, 조작한 요소, 입력한 값, 그 결과를 읽어 내고 가장 가능성이 높은 시나리오 하나를 고릅니다. 그 해석을 실제 브라우저에서 확인한 뒤 스크립트를 만들며, 어떤 근거로 그 시나리오를 골랐고 어떤 해석을 왜 버렸는지 결과의 근거란에 적습니다. 화면을 알아볼 수 없거나 서로 관련 없는 흐름이 섞여 있으면 임의로 지어내지 않고 사람 확인이 필요한 상태로 돌려보냅니다.

영상은 `ffmpeg`로 시간 순서의 화면 여러 장으로 나누어 전달합니다. `ffmpeg`가 설치되어 있지 않으면 영상에서 화면을 뽑지 못했다고 알리므로 캡처 이미지를 함께 올려 주세요. 첨부 파일은 증거 폴더의 `requests/<시각>/` 아래에 보관하며, 실패 증거와 같은 기간(`evidence.retain_fail_days`)이 지나면 정리됩니다.

## 사용할 AI 선택 (LLM 설정)

**LLM 설정** 화면에서 검증을 수행할 AI를 고릅니다. 선택한 내용은 프로젝트 레지스트리 옆 `agent-settings.json`에 소유자만 읽을 수 있는 권한으로 저장하며, 다음 요청부터 적용됩니다.

| 선택 | 실행 방식 | 인증 |
|---|---|---|
| 관리자 기본 설정 | `vigil.yaml`의 `agent.models` 체인 | 서버 환경 변수 |
| 내 API 키 | vigil의 pi 에이전트를 내 키로 실행 | Anthropic, GLM Coding Plan(Z.ai), OpenAI, 또는 OpenAI 호환 엔드포인트(주소와 모델 입력) |
| 내 코딩 에이전트 | 이미 로그인한 CLI를 그대로 사용 | Claude Code, Codex, pi의 자체 구독. 키를 저장하지 않습니다 |

API 키는 화면에 다시 표시하지 않고 끝 네 자리만 보여 줍니다. 저장 전에 제공자의 모델 목록으로 연결을 확인하므로, 키나 모델 이름이 틀리면 저장되지 않고 그 자리에서 알려 줍니다. OpenAI 호환 엔드포인트는 vigil이 생성한 pi 확장으로 등록하므로 개인 `~/.pi/agent/models.json`을 수정하지 않습니다.

내 코딩 에이전트를 선택해도 규칙은 같습니다. 같은 시스템 프롬프트와 같은 결과 형식을 쓰고, 브라우저 조작은 `vigil mcp-browser`가 MCP로 제공하는 도구로만 합니다. 어느 쪽도 대상 서비스 코드를 수정할 수 없지만, 격리 수준은 다릅니다.

- **Claude Code**: `--restricted`와 `--strict-mcp-config`로 실행하며 브라우저 도구와 파일 읽기 도구만 허용합니다. 셸이 없고 vigil이 제공한 MCP 서버 외에는 보이지 않습니다.
- **Codex**: `codex exec --ignore-user-config -s read-only`에 승인 정책 `never`, vigil 브라우저 도구만 사전 승인한 상태로 실행합니다. Codex 자체의 읽기 전용 셸은 그대로 있어 작업 중 로컬 파일(예: `~/.agents`의 스킬 문서)을 읽을 수 있습니다. 쓰기와 승인이 필요한 작업은 거부됩니다.

## 프로젝트와 사이트

프로젝트 선택은 URL의 `project` 값에 저장됩니다. 서로 다른 탭에서 다른 프로젝트를 열어도 선택이 섞이지 않습니다. 검색, 필터, 증거 링크에도 선택한 프로젝트가 유지됩니다.

첫 프로젝트는 지정한 기존 설정의 데이터베이스와 증거를 사용합니다. 새 프로젝트는 레지스트리 옆 `projects/<id>/` 아래에 별도 데이터베이스와 증거를 만듭니다. 기존 프로젝트의 계정과 수집기 설정을 새 프로젝트로 복사하지 않습니다. 같은 스크립트 ID도 프로젝트가 다르면 별개로 관리됩니다.

프로젝트와 사이트 설정은 기본적으로 state 디렉터리의 `admin-projects.json`에 저장됩니다. `--registry`로 경로를 지정할 수 있습니다. 저장은 임시 파일에 쓴 뒤 원자적으로 교체하며, 재시작해도 유지됩니다. 기존 YAML 파일 자체는 덮어쓰지 않습니다. `admin`에서 변경한 URL을 별도 `loop`/CLI 실행에 적용하려면 해당 설정을 별도로 맞춰야 합니다.

등록된 프로젝트·사이트 ID는 유지합니다. 이름과 URL은 변경할 수 있고 사이트를 추가할 수 있습니다. 삭제는 제공하지 않습니다. 실행 중에는 해당 프로젝트의 사이트 변경을 거부합니다. 두 화면에서 동시에 편집하면 먼저 저장한 변경을 덮어쓰지 않고 다시 불러오도록 안내합니다.

DSL의 `goto: "#"`는 선택한 사이트의 전체 URL을 사용하며 경로와 query도 유지됩니다. 결과 화면은 사이트별 최신 실행을 구분하며 배포 식별자가 없어도 실제 결과를 표시합니다. 새로고침 후에는 저장된 결과를 다시 읽습니다.

고급 스크립트에 절대 URL이 명시된 경우 URL 설정을 바꿔도 그 스크립트 본문은 자동으로 다시 쓰지 않습니다. 실행 시 허용 호스트 정책으로 범위를 확인합니다.

## 실행 방식

`admin`은 사용자가 요청한 검사만 실행합니다. 요청한 시나리오의 에이전트 탐색과 독립 검증을 자동 처리합니다. 정기 스케줄러와 Jira 알림은 시작하지 않습니다. 기존 `loop --ui`와 ProofQA 명령은 계속 사용할 수 있습니다.

브라우저 창은 기본적으로 표시됩니다. 서버나 자동화 환경에서는 `--headless`로 숨길 수 있습니다. 검사가 끝나면 소유한 브라우저를 닫아 자원을 반환합니다.

프로젝트마다 한 번에 한 검사를 실행합니다. 실행할 사이트와 브라우저는 검사 실행 메뉴에서 선택할 수 있습니다. 실행은 등록 시점의 설정으로 진행되며 원본 결과와 증거를 남깁니다. 연결이나 브라우저 시작에 실패하면 환경 오류로 기록됩니다.

**검증 결과**의 발견된 문제마다 **재확인** 버튼이 있습니다. 결함을 고친 뒤 누르면 같은 사이트·브라우저 선택으로 그 검사를 다시 실행하고, 검사 관리의 실행 패널에서 진행 상황을 보여 줍니다. 검사가 통과하면 문제는 해결로 닫히고, 실패하면 열린 채 남습니다. 검사를 반려하면 그 검사의 문제도 닫힙니다. 실행 중에 반려된 검사는 결과만 기록하고 새 문제를 열지 않습니다. 검사 환경 문제는 이후 어떤 검사든 사이트에 도달하면 닫힙니다.

관리 콘솔은 literal loopback 주소에만 바인딩하며, 로컬 Host와 같은 출처의 변경 요청만 허용합니다. 새 조직용 로그인·권한 시스템은 이번 기능에 포함하지 않습니다.

## 검증 명령

```sh
go test ./...
go vet ./...
```

`internal/admin/console_test.go`는 저장/재시작, 프로젝트 분리, 잘못된 URL, 다른 출처의 변경 요청, 오래된 수정 요청과 실행 중 URL 변경 거부를 검증합니다. `internal/orchestrator/draft_test.go`는 프로젝트별 검사 등록, 승인 대기 유지와 기존 ID 덮어쓰기 거부를 검증합니다.

실행한 검증 범위와 한계는 [검증 기록](admin-verification.md)에 정리했습니다.
